Rendering

The exact same menu tree can render two different ways — you pick per menu, and every component works under both.

Dialog vs. inventory

Render typeSelected withRenders as
DIALOG (default)menu.dialog() / type="dialog"Mojang's native dialog UI.
INVENTORYmenu.inventory() / menu.inventoryRows(n) / type="inventory" / rows="n"A classic chest-style inventory GUI, n rows tall (1–6, clamped).
Menu inventoryMenu = Menu.create("myplugin:shop-inv")
    .inventoryRows(4)
    .title("Shop")
    .row(row -> row.button("Buy Sword").icon("diamond_sword").action("myplugin:buy.sword"));

Everything documented in Components and XML Markup applies identically to both render types — the same markup or builder chain just needs a different type/renderType().

How dialog rendering works

  • Text and Icon elements become the dialog's body content, in order.
  • Button elements become dialog action buttons, laid out in a grid sized to the menu's content.
  • close-on-escape maps directly to whether the dialog can be dismissed with Escape.
  • If a button's enabled-if/enabledIf condition is false when clicked, the click is rejected with "You can't do that right now." instead of dispatching the action.

Inputs & submit

<input> elements render as native form fields (text box, toggle, number slider, or single-choice picker, depending on type). Their current values are collected whenever any button in the menu is clicked, not just a designated submit button.

If you set submitAction / submit-label on the menu, HTMLib adds one more button automatically that fires that action id with source() == null:

Menu menu = Menu.create("myplugin:shop")
    .submitAction("myplugin:shop.checkout")
    .submitLabel("Buy")
    .add(new Input("quantity").numberRange(1, 10, 1, 1).label("Quantity"));

HTMLib.registerAction("myplugin:shop.checkout", event -> {
    Float quantity = event.inputNumber("quantity");
    // ...
});

Read submitted values back through ActionEvent.inputs() or its typed accessors.

Notes

Image rendering: an <image> element currently always renders using its fallback-icon material rather than an arbitrary image source — pick a representative item icon for now.
